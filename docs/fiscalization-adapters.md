# Fiscalization adapters

This document describes the seller-aware fiscalization layer and the built-in selectable provider adapters. It is not a certified fiscal product. Provider credentials, seller account setup, country mappings, deployment topology, sandbox acceptance, and legal approval are still required before production.

## Model

- A legal seller is separate from an organizer/partner account.
- A ticket type maps to exactly one legal seller and one seller-of-record mode: `organizer_seller` or `platform_seller`.
- The invoice issuer of a Pass Captain order is decided by `Partners\SalesModel` (seller key `platform` or `org-{partner_id}`); one order has exactly one issuer, and WooCommerce carts with several issuers are rejected or split into one Pass Captain order per issuer (`Integrations\WooCommerce\SellerSplit`, docs/WOOCOMMERCE.md). The fiscal legal seller must agree with it: platform tickets use `platform_seller`, tickets of an agent organizer `organizer_seller` (checked when a ticket type is assigned and again at checkout), all fiscally mapped ticket types of one order belong to one legal seller, and mapped and unmapped ticket types are never mixed in one order.
- During the `wpcap_order_creating` transaction the module stores an immutable seller/profile snapshot per mapped ticket type and freezes one fiscal document per (Pass Captain order, legal seller). Non-ticket WooCommerce lines with their own legal seller get their own document in that order. Ticket line amounts are the amounts actually paid (after campaign discounts; for WooCommerce the allocated line totals).
- Each document gets a stable SHA-256 idempotency key based on the Pass Captain order and seller. Gross, tax, currency, seller identity, seller mode, payment channel/method, provider ID, and non-secret provider configuration are snapshotted. Retries and manual reconciliation use this original configuration even if the seller later switches providers; credentials are resolved separately at call time. Later profile edits do not change an existing document.
- Ticket issue is gated by `wpcap_order_fiscal_ready`. Mapped orders do not issue tickets until every seller document has status `submitted`. An explicit reviewed `not_required` profile is supported; without any seller mapping, existing sales keep their previous behavior. A missing or unsupported active profile blocks the mapped order before payment.
- Failed calls retry with exponential delays, capped at eight automatic attempts. An append-only event table records submission, status lookup, and reconciliation checkpoints without storing raw provider response bodies. The admin screen can reconcile ambiguous operations and restart terminal failures.

## Provider adapter contract

Implement `PassCaptain\\Fiscalization\\AdapterInterface` (contract version 2) and register it with the `wpcap_fiscal_adapters` filter. An adapter reports country codes and machine-readable capabilities, implements a non-mutating health check and an idempotency-key status lookup, and submits normalized receipts. Every adapter must declare the core capabilities `receipt_submit` and `operation_status`; profiles may require more. The adapter must:

1. Return a stable lowercase provider ID from `id()`.
2. Declare the supported country codes from `countries()`.
3. Implement `submit($document, $seller, $configuration)`.
4. Use `$document['idempotency_key']` for every remote submission. On retries the core calls `query_status()` first; only an explicit `not_found` permits another submit. An unknown status blocks ticket issuance and submission.
5. Return an array with a non-empty stable `reference` on success, or a `WP_Error` on failure. Printable QR/signature/receipt fields belong in that result and should be rendered only by a later provider-aware ticket/receipt view.
6. Keep API secrets out of the general configuration table (configuration keys that look like secrets are refused). Credentials per seller/provider are stored with the plugin's secrets vault (`Security\Vault`, libsodium secretbox; master key `PASS_CAPTAIN_SECRET_KEY`, otherwise derived from the wp-config salts; see docs/SECURITY.md). Each entry is encrypted for the context `fiscal_credentials:{seller_id}:{provider_id}`, so a copied ciphertext does not decrypt for another seller/provider. Key rotation: keep the old key in `PASS_CAPTAIN_SECRET_KEY_PREVIOUS`; entries are re-encrypted on use and by the vault migration (vault version 3). Entries of the earlier draft format (AES-GCM from the salts) are migrated once. Without libsodium or a key, saving credentials is refused (never stored in plaintext). Values are never redisplayed, returned through REST or written to the audit log; decrypted values are registered with `Security\Redact` for the rest of the request. fiskaly access tokens are cached encrypted.
7. The core also resolves optional external credentials at call time through `wpcap_fiscal_credentials` and adds them as `$configuration['credentials']`. The filter receives `( $credentials, $seller_id, $provider_id )`; return only the requested seller/provider's secrets. Filter-provided values override the same vault keys. Adapters must not log credentials or include them in provider error messages.

The core never selects a vendor automatically. Each legal seller can select its own provider and non-secret configuration; credentials are held separately in the encrypted vault.

## Built-in provider adapters

| Adapter ID | Countries declared by this adapter | Required setup |
| --- | --- | --- |
| `fiskaly_sign_at` | AT | SIGN AT account credentials, cash register ID, reviewed receipt schema |
| `fiskaly_sign_de` | DE | SIGN DE credentials, TSS/client IDs, VAT-rate and payment-type mappings |
| `fiskaly_sign_unified` | FR, IT, PT, SE | Unified API credentials, system/scope IDs, country VAT and payment mappings |
| `efsta_efr` | AT, BE, CZ, DE, DK, ES, FR, HR, HU, IT, LT, NO, PL, PT, SE, SI, SK | Reachable EFR endpoint, register/terminal IDs, tax-group and payment-group mappings |
| `fiskaltrust_pos` | AT, BE, DE, ES, FR, GR, IT, PT | Cashbox ID/access token, POS system ID, receipt case, charge-item and payment mappings |

These country lists describe adapter routing declarations only. They do not mean every deployment, sales channel, ticket format, refund path, or legal regime is supported or certified. In particular, this implementation does not claim fiskaltrust coverage for HU, nor fiskaly SIGN ES. The customer chooses among adapters that declare the seller's country; unsupported combinations remain blocked.

All adapters use one transport, `PassCaptain\Fiscalization\ProviderHttp`, built on `Security\OutboundHttp`: HTTPS to public addresses only (the host is resolved; loopback, private, link-local/metadata, CGNAT, reserved and documentation ranges and credentials in the URL are refused), no redirects, timeouts of 2–15 seconds, a 512 KiB response limit, amounts formatted with the decimals of the document currency, and failures logged through `PassCaptain\Log` with host and error code only. Endpoints in a provider configuration (`*_url` keys) are validated when saved.

The efsta and fiskaltrust adapters call an endpoint configured by the site operator. A local service (e.g. efsta EFR on `http://127.0.0.1:5618`) is only reachable when the setting **Lokalen Fiskaldienst erlauben** (`fiscal_allow_local_service`, filter `wpcap_fiscal_allow_local_service`) is enabled, and then plain HTTP only to loopback/private addresses, never across the internet. No local daemon is installed by this plugin.

fiskaly has multiple API families, not one interchangeable endpoint: SIGN AT and SIGN DE are separate adapters; FR/IT/PT/SE use the Unified API adapter. For Unified API ambiguous retries, the adapter only repeats creation calls within a conservative 20-hour window; older operations require manual provider-dashboard reconciliation to avoid duplicate fiscal records.

The efsta adapter additionally exposes a narrowly scoped, one-time full-void action for eligible AT and DE order cancellations that were cancelled before payment. It uses the frozen original seller/document snapshot and EFR's `/register/void` endpoint. A durable one-shot lock prevents automatic resubmission after any attempt; an ambiguous or failed result requires checking EFR and recording the provider reference manually. This is not a refund, partial return, event cancellation, or Hungary workflow. HU corrections remain manual because the stored transaction does not yet capture all country-required correction data. fiskaly and fiskaltrust correction/refund operations remain manual.

Other country-specific correction/void and refund credit-note workflows, authority exports, provider certification, customer sandbox acceptance, and hardware commissioning remain separate production work. Run only the exact provider/country/seller/channel/payment combinations that have passed those checks.

## Box office shift closing (optional)

An adapter may additionally implement `PassCaptain\\Fiscalization\\ClosingAdapterInterface` (`close_shift( $closing, $seller, $configuration )`, capability key `shift_closing`). When the box office setting `boxoffice_fiscal_closing` is enabled (default off), `Fiscalization\\ShiftClosing` listens to `wpcap_boxoffice_shift_closed` and calls `close_shift()` once per (Z report, legal seller) for the sellers of the shift's fiscal receipts and the sellers with an active production POS profile for the shift's location/register. `$closing` carries a stable `idempotency_key`, the Z number and hash, register scope, period, the register's Z totals and the seller's confirmed receipts (count, gross, tax, document keys). The result (`reference` required, optional `signature` and scalar `fields`) is appended to the fiscal event log as `shift_closing` (document_id 0) with status `submitted`, `failed`, `unsupported` or `unavailable`; there is no automatic retry. The Z report shows a "Fiskalisierung" section per seller through `wpcap_boxoffice_zreport_html_extra`. No built-in adapter implements the closing yet; provider-specific day-end/closing requests remain production work.

## Hooks

- `wpcap_fiscal_adapters` (filter): adapter list; built-in adapters are added at priority 5.
- `wpcap_fiscal_credentials` (filter): `( array $credentials, int $seller_id, string $provider_id )`.
- `wpcap_fiscal_profile_scope` (filter): `( array $scope, string $channel, array $internal, int $order_id )`.
- `wpcap_order_fiscal_ready` (filter): `( bool $ready, int $order_id )`; false withholds ticket issuance.
- `wpcap_fiscal_terminal_failure` (action): `( array $details )` after a terminal failure.
- `wpcap_woocommerce_fiscal_item_seller` (filter) and `wpcap_woocommerce_non_ticket_refund` (action, first argument: list of Pass Captain order IDs of the WooCommerce order).
- `wpcap_event_cancelled` (action) and the extended `wpcap_order_cancelled` (`int $order_id, string $reason, string $previous_payment_status`).

See docs/HOOKS.md for the complete list.

## Admin REST endpoints

All endpoints require an authenticated user with `manage_options`:

- `GET /wp-json/pass-captain/v1/fiscal/sellers`
- `POST /wp-json/pass-captain/v1/fiscal/sellers` with `legal_name`, `country_code` (supported ISO country code), and seller tax/address details
- `POST /wp-json/pass-captain/v1/fiscal/sellers/{seller_id}/profiles` with the seller/channel scope, optional `location_id` and `register_id`, environment, status, reviewed rule-set/version, legal reference, and additional required capability keys; optional `effective_from`/`effective_until` as `Y-m-d H:i:s` (UTC) or ISO 8601 with offset (stored in UTC; other formats or an end before the start return HTTP 400 with `data.field`)
- `PUT /wp-json/pass-captain/v1/fiscal/sellers/{seller_id}/provider` with `provider_id`, `enabled`, and non-secret `configuration`
- `POST /wp-json/pass-captain/v1/fiscal/sellers/{seller_id}/health-check` runs a provider health check without creating a receipt
- `PUT /wp-json/pass-captain/v1/fiscal/ticket-types/{ticket_type_id}/seller` with `seller_id` and `seller_mode`
- `POST /wp-json/pass-captain/v1/fiscal/events/{event_id}/manual-resolution` records a provider correction completed outside the plugin; requires `resolution` (`void`, `refund`, `credit_note`, or `correction`) and a provider reference
- `POST /wp-json/pass-captain/v1/fiscal/documents/{document_id}/reconcile` queries an ambiguous provider result
- `POST /wp-json/pass-captain/v1/fiscal/orders/{order_id}/retry` to retry terminal failures

Example seller modes are `organizer_seller` (organizer is seller and invoice issuer) and `platform_seller` (central operating company is seller and issuer). The selected entity must be a legally correct seller for the transaction. Profile activation records the reviewer, reference, and profile version. `not_required` must be an explicit reviewed decision; the system does not infer an exemption from the country alone.

## Refunds, cancellations, mixed carts, and outages

- A completed partial or full refund is recorded in the append-only fiscal event log as `refund_adjustment / manual_required` for the affected seller receipt. The event records refund amount, currency, ticket references, whether refunded tickets were already checked in, and whether seller allocation is ambiguous. The original receipt is never edited. WooCommerce refunds for non-ticket products, fees, and shipping are matched against the original fiscal snapshot's WooCommerce line key and recorded against that seller document. Missing or unmatched source lines, including amount-only WooCommerce refunds without a referenced original line, are explicitly flagged as requiring manual seller allocation.
- Already checked-in tickets remain as historical check-ins when refunded; they are flagged as used in the correction event. The cashier/admin must resolve the event with the selected provider's country-specific refund, credit-note, correction, or void flow. The admin screen can append the provider reference after that external action and prevents duplicate resolution entries; this is an audit record and does not submit a correction receipt. No built-in adapter currently submits those adjustments automatically. The adapter contract currently covers receipt submission and status recovery only; correction capability is intentionally not advertised until provider-specific request schemas, reference handling, retries, and country validation are implemented.
- Cancelling an order records a `void` task when no payment had been exchanged and a `refund_or_correction` task when the prior payment status was paid. Event cancellation records a task for every submitted fiscal document containing tickets from that event. Any provider-required references and country-specific deadlines remain the seller's responsibility until an adapter implements the relevant correction capability.
- WooCommerce applies coupons and line discounts before Pass Captain snapshots each line. Fiscal documents group the final gross and tax amounts by legal seller; the plugin does not calculate or distribute seller payouts. Mixed carts may contain mapped tickets, ordinary products, fees, and shipping only when every non-ticket line has an explicit legal seller assignment. Ordinary products use the product editor fields `_wpcap_fiscal_seller_id` and `_wpcap_fiscal_seller_mode`; fees and shipping use those order-item metadata keys or the trusted `wpcap_woocommerce_fiscal_item_seller` filter. The filter receives the item, order, and line type and must return a valid seller assignment. Unassigned lines block checkout before payment, as does a non-ticket line with multiple tax rates. Negative fees keep the WooCommerce allocation rule (share per seller's tickets and shop, largest remainder): the ticket share reduces the ticket lines and is therefore represented on the receipt. A share falling on non-ticket products cannot be represented; while a receipt is required for the order's tickets (active production profile), checkout is refused with a hint to use coupons (`wpcap_fiscal_negative_fee`). With a reviewed `not_required` profile or without fiscal mapping, the previous behaviour is unchanged. Assigned non-ticket lines are included in the seller's fiscal document using WooCommerce's final post-discount line totals and are attached to the split order whose tickets have the same legal seller (otherwise the first fiscally mapped split order). Precedence rules: docs/WOOCOMMERCE.md, "Fiskalbelege je Verkäufer".
- The default outage policy is `stop_sale`: tickets remain blocked until the provider confirms the receipt. At the box office the sale stays `pending` without receipt number (`wpcap_pos_fiscal_pending` / `wpcap_pos_fiscal_failed`); the cash session cannot be closed while it is unbooked, and "Nachbuchen" books it once the receipt is confirmed. A database error in the fiscal gate blocks issuance (fail closed). Automatic retries honour a stored backoff (`next_attempt_at`); operator retry and reconcile run immediately. The profile may declare `provider_buffered` only with the required `offline_issue_queue` adapter capability; no built-in adapter currently advertises it. A background retry queue is recovery after a request, not permission to issue an unconfirmed fiscal ticket.

## Operational behavior

The profile selector uses exact `location_id` and `register_id` values. A trusted deployment or POS integration can provide them through `wpcap_fiscal_profile_scope( $scope, $channel, $internal, $order_id )`; customer request data is not used to choose a fiscal profile. For POS sales the default scope comes from the active cash session's `location_id` and `register_id`; other channels default to location `0` and an empty register ID unless an integration supplies a scope. An unmatched scope blocks mapped sales rather than falling back to a broader profile. Administrators can manage location/register pairs from the box-office settings using one `location_id|register_id|display_name` row per terminal. Once the directory contains entries, the cashier selects a listed register; the server validates the pair on session creation and on every sale. Removing a register blocks new sales from an open session using that register, while still allowing the cashier to close it. Empty configuration preserves existing installations' manual IDs until the directory is enabled. Existing sessions keep their frozen scope, and removing a register does not rewrite past session records.

The POS accepts an optional `payment_method` (`cash`, `card`, `voucher`, or `other`) and snapshots it for adapters. WooCommerce snapshots its configured payment gateway ID. The POS response adds `tickets_issued` and `ticket_issuance_pending`. WooCommerce receives an order note when payment is accepted but the fiscal adapter has not yet completed and tickets are still withheld. Operators must monitor these orders and resolve terminal failures with the retry endpoint after confirming the provider's status. Permanent configuration/capability failures stop retrying immediately. Terminal failures are written to the audit log, emit `wpcap_fiscal_terminal_failure`, and send a notification to the WordPress admin email; notifications contain identifiers and error codes, not provider response bodies or credentials.

## Remaining implementation before production

- Complete provider sandbox acceptance and country/profile qualification for each customer-selected built-in adapter. The admin can store credentials in the encrypted per-seller/provider vault or a trusted site integration can resolve them through `wpcap_fiscal_credentials`.
- Improve the initial admin screen with seller editing/deactivation, clear credential-availability status, richer order-level fiscal diagnostics, and credential vault backup/rotation procedures.
- Complete provider-aware QR/signature output for all receipt paths and country-required archive/export flows. The first renderer shows normalized receipt fields and a separate fiscal QR on POS receipts and WooCommerce order details; a bounded normalized CSV export is available for operations, but it is not an AT, DE, or HU authority format. QR is omitted from the existing POS storno receipt until a fiscal correction exists.
- Implement and validate provider-side execution for seller-specific fiscal adjustments: partial/full refunds, credit notes, cancellation/void protocols, operator/day-end exports, and HU NAV reporting. WooCommerce/native refund accounting, ticket revocation, and seller allocation/audit events are implemented, but the plugin does not submit a fiscal correction receipt yet. Do not enable production profiles that require correction support until the selected adapter reports and passes the required correction capability.
- Confirm any provider-buffered offline procedure against the exact country/provider rules. Current default is stop-sale and none of the built-in adapters declares offline issuance. The implementation does not make provider or tax-authority calls until the seller enables a reviewed profile.

The national legal requirements and provider certification must be validated for each exact seller, sales channel, payment method, and deployment. This adapter layer does not make those determinations.
